# accommerce-inventory

A single-tenant Stock+Money platform for Accommerce (the Jello brand) — built to eventually replace their Google Sheets "Control Tower" as the operational source of truth for purchase orders, shipments, payments, and inventory. Node/Express + tRPC + React + TiDB (MySQL) via Drizzle ORM.

This started as a **V1 skeleton** and has since gone through seven hardening passes (Backlog Stream B: migration & cutover readiness; Backlog Stream A: wiring completion; Backlog Stream E: systemic correctness hardening; Backlog Stream C: security hardening; Backlog Stream D: performance hardening; Backlog Stream G: inventory ledger completion & navigation restructuring; Backlog Stream H: weekly sales plan input & generation) — every stream in the original post-V1 backlog is now done, plus Streams G and H, added afterward at the user's request. The ledger-centric core, auth, and the Stock/Purchase Orders/Shipments/Transactions/Cost & Cashflow/Catalog pages are built and tested, every page's manual-entry gaps (creating a new shipment, a new PO) are closed, the schema/migration tooling is real (foreign keys, negative-stock validation, quarantine-not-abort migration handling), every piece of backend logic V1's own review found "built, tested, but unreachable" now has a real router procedure and UI, the daily Shopify pull is idempotent with a pinned-UTC connection timezone and enforced landed-cost currency matching, auth runs on real per-user credentials with session revocation and a per-email login throttle, the Home/Stock/Money dashboards scale to real SKU volume via grouped aggregate queries instead of one-query-per-SKU loops, a shipment marked arrived now atomically writes a real inventory ledger receipt at its real landed cost (previously only a one-time migration script could ever do this), a `sales_plan` day can no longer silently exist as a duplicate row, and the business can plan sales 26 weeks ahead from weekly revenue and a product mix instead of typing one SKU/day entry at a time — but it has not yet run against real Control Tower data — see [Current Status](#current-status) below before assuming this is production-ready.

## Architecture in one paragraph

`inventory_ledger` is the single append-only source of truth for stock and landed cost — SOH, Daily COGS, and Cashflow are always computed live from it and from `payments`/`transactions`, never stored as separate fields. Every client gets their own physically isolated deployment from the same code/schema template (no shared multi-tenant database, no `tenant_id` column anywhere) — this instance is Accommerce's own. Every field-level change to a Purchase Order, Shipment, or Payment that affects delay or cost writes an audited `change_log` row with a required reason category.

## Local development

```bash
cp .env.example .env   # fill in DATABASE_URL / SESSION_SECRET
docker compose up -d   # local MySQL 8 for dev/test (see docker-compose.yml)
pnpm install
pnpm db:push
pnpm dev                # server on :3000, Vite client via the /api proxy
```

Run the test suite with `pnpm test` (source `.env` into your shell first — `set -a && source .env && set +a` — vitest doesn't load it automatically; see `docs/BACKLOG.md` section F).

## Current Status

- **V1** (20 build tasks): each individually reviewed; one whole-branch review found and fixed 3 Critical + 3 Important issues (login flow, production static serving, a currency-blending bug, a broken test command, a wrong stockout-risk calculation, a dashboard not rendering data it already had).
- **Backlog Stream B — migration & cutover readiness** (10 build tasks, done 2026-09-14): real foreign keys on every core ownership edge, negative-stock validation, a SKU-identifier uniqueness constraint, a shipment status state machine, migration scope widened to the full PO/Shipment/Payment/Transaction history with quarantine-not-abort handling for malformed rows, atomic single-transaction migration, tolerance-based landed-cost reconciliation (built and tested, not yet wired to a live data source), and real CLI entrypoints. One whole-branch review found and fixed 2 Critical + 6 Important cross-task issues.
- **Backlog Stream A — wiring completion** (8 build tasks, done 2026-09-19): every piece of backend logic V1's own review flagged as "built, tested, but unreachable" now has a real router procedure and UI — sales plan entry, shipment progression past `departed` with customs status and actual arrival date tracking, a dedicated depart-date correction path, payment history, real payment/shipment re-listing on page reload, and a genuine transaction-matching UI. One whole-branch review found and fixed 2 Critical + 2 Important cross-task issues, including a real data-corruption path (a UI control that could permanently strand a shipment with no way to record its actual depart date) and a silent payment double-matching hole.
- **Backlog Stream E — systemic correctness hardening** (6 build tasks, done 2026-09-19): the daily Shopify pull is now idempotent with a real CLI entrypoint; `purchase_orders.plannedReadyDate`, `sales_plan.periodDate`, and `sales_actuals.date` are genuine calendar-day types with no timezone-conversion drift, `inventory_ledger.date` keeps Stream B's `timestamp(3)` precision fix behind a pinned-UTC connection timezone; landed-cost computation throws on a currency mismatch instead of producing nonsense. Two of the six tasks required a fix round that corrected the plan's own specified technical mechanism, not just an implementation bug (a mysql2 connection option that turned out to do nothing; a midnight anchor for derived ledger events that broke same-day event ordering) — both caught by task review and independently re-verified against real library source and a live database before being accepted. One whole-branch review found and fixed 6 Important cross-task issues in one wave, no Critical findings at any stage — including a genuinely latent negative-stock-guard bug this stream's own anchor-time choice introduced, found and closed within the same stream rather than shipped.
- **Backlog Stream C — security hardening** (5 build tasks, done 2026-09-20): real per-user credentials (`users.passwordHash`) replace the shared `APP_PASSWORD` identity-picker, closing the actual role boundary; session revocation via a `tokenVersion` counter means logout or a password reset invalidates a session immediately instead of leaving a 365-day token valid regardless; a real sign-out control now exists in the UI; a per-email login throttle locks an email out after 5 failed attempts. The final whole-branch review found and fixed 1 Critical + 4 Important issues: the Critical was the throttle keying its lockout on the raw, case-sensitive email string, letting an attacker bypass the 5-attempt limit entirely via case permutation of the same address.
- **Backlog Stream D — performance hardening** (3 build tasks, done 2026-09-20): `getHomeSummary`, `getStockDashboard`, and `getMoneyDashboard`'s Daily COGS path no longer issue one database query per SKU (or per day) — new grouped aggregate queries (`getSohForSkus`, `getAverageDailySalesForSkus`) and a single chronological forward-pass FIFO computation (`getDailyCogsForRange`) replace what were tens of thousands of sequential round trips (and, for Daily COGS, full-history FIFO recomputation) at a realistic SKU count. Every dashboard's output was verified byte-identical to pre-refactor behavior, not just assumed. The final whole-branch review found only Minor findings (documentation precision, one test-strength tightening) — no Critical or Important issues at any stage across all three tasks.
- **Backlog Stream G — inventory ledger completion & navigation restructuring** (7 build tasks, done 2026-09-20, added after the original post-V1 backlog at the user's request): a shipment marked arrived now atomically writes a real `inventory_ledger` receipt per line item at its real landed cost — previously only a one-time migration script could ever write a receipt, meaning the live app had no way to actually receive new stock after a real go-live. Frontend navigation restructured to match the 13-tab Google Sheets Control Tower structure: Stock gained an FF/Mutual warehouse toggle, Money was cleaned up and relabeled "Cost & Cashflow," and two new pages (Transactions, Catalog) plus a new Inventory Ledger batch-detail drill-down were added. The final whole-branch review found and fixed 1 Critical + 5 Important + 1 Minor in one wave: the Critical was `markShipmentArrived` having no guard against being called twice, which would have silently doubled a batch's inventory forever (no reversal path exists anywhere in this codebase); the same fix closed a related Important finding that `"delivered"` status was reachable via a different function entirely, bypassing the ledger write and cost guard. A same-day follow-up fixed a genuine, pre-existing bug this stream's own manual QA surfaced (`dashboards.money` crashing on mixed-currency unpaid payments) and closed the shipment/PO manual-entry gaps the stream's own final review flagged — both now have real create forms.
- **Backlog Stream H — weekly sales plan input & generation** (4 build tasks, done 2026-09-20, added after Stream G at the user's request): `sales_plan` gained a real uniqueness constraint (re-entering a plan for a day no longer silently duplicates it) and a way to plan sales at the grain the business actually uses — enter a week's revenue, a per-SKU units-per-€1,000 mix, and a warehouse-split percentage, and the system computes and writes the day-by-day, per-SKU, per-warehouse breakdown, 26 weeks ahead, independently revisable week by week. Two genuine design-level gaps (not implementation bugs) were found and closed during the build itself: a recipe change alone, and separately a warehouse reassignment alone, each left stale rows behind under the old state — unified into one rule that cleans up every SKU from the previous save under the previous warehouse pair before every regeneration. The final whole-branch review independently re-verified that twice-revised logic from scratch before finding and fixing 4 Important + 2 promoted issues in one wave: no numeric validation on the revenue/percent/ratio inputs (a percent over 100 silently wrote a *negative* planned quantity), a test suite with 22 hardcoded date literals that would put it in the past within a month, a migration adding a uniqueness constraint with no de-duplication step against data the design's own spec says already has live duplicates, and a circular import between two server modules that only worked by accident of function-hoisting.
- **Backlog Stream I — three-lens architecture review** (done 2026-09-20, at the user's request): the first review in this engagement to examine the whole system's accumulated cross-stream interactions rather than one stream's own diff — three independent fresh reviews (operational excellence, product coherence, engineering rigor), each exploring the codebase cold. Found roughly 40 real issues; the most severe and cross-confirmed six were fixed immediately (all going through the same review → fix-round → scoped-re-review cycle as every other stream), the rest tracked in `docs/BACKLOG.md` section I for future prioritization. Fixed: a shipment cost-allocation input (`weightShare`/`valueShare`) that could silently write a corrupted, permanent, unrecoverable landed cost into the ledger — flagged independently by all three lenses; a real divergence between two of three parallel FIFO implementations on how they handled inventory adjustments, which the fix's own first attempt introduced a new timing hazard into before a fresh re-review caught it; two competing Sales Plan input UIs on the same page silently overwriting each other's data; a currency-casing bug that could crash both the Home and Money dashboards; a SKU-creation form guaranteed to fail for 4 of its 6 offered options; and a dead, misleading duplicate type export.
- **Post-Stream-I operational cleanup** (done 2026-09-20, at the user's explicit priority ordering — operational first, then engineering, then product): every bounded item Cook's lens flagged in `docs/BACKLOG.md` section I is now fixed — production deploys must use `db:migrate` (not `db:push`, which risks authoring an unintended migration at deploy time); `nightlyExport.ts`'s table list was missing Stream H's 2 sales-plan-input tables; matching a transaction to a payment now atomically marks it paid using the transaction's own amount/fxRate/date (previously the two "is this paid" signals silently disagreed forever); real UI now exists to advance a PO's status and to record a bank transaction; Home now surfaces overdue payables (previously invisible — the near-term cash window only ever looked forward) and correctly flags a SKU with zero ledger history as stockout risk instead of silently safe; the Cost & Cashflow page's Daily COGS/Landed Cost tabs now have real SKU/warehouse/shipment pickers instead of silently scoping to whichever entity happened to be first in the list. Deliberately deferred (need a real design pass or external infra decisions, not bounded fixes): reversal/correction paths for stock/cost/payment data, freight/duty lock-after-arrival, the nightly export's unbounded-query OOM risk, Shopify pull scheduling/alerting, and monitoring/restore-drill infrastructure.
